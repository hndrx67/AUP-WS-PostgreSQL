01 / UNDER THE HOOD

System architecture

Browser UI talks to Next.js. PostgreSQL is reached only from server code using a pooled connection.

Database calls and authorization checks run on the server. Server-rendered list pages use a PostgreSQL query helper; actions use parameterized SQL and transactions. Do not put the connection string in any NEXT_PUBLIC_* variable.

App pages & actions

app/(app)/ contains role-based screens. app/actions/ contains sign-in, profile, time, schedule, department, user, kiosk, and finance operations.

Server libraries

lib/db.ts connection pool and transactions · lib/auth.ts sessions and role gates · lib/postgres-client.ts page-read helper · lib/finance.ts balance calculations.

Database & scripts

database/schema.sql initial schema · scripts/migrate.mjs schema runner · scripts/create-admin.mjs first administrator bootstrap.

02 / WHO USES IT

Roles & capabilities

Users sign in with an assigned email and password. Administrators create accounts; public self-registration is not used.

WORK SCHOLAR · STUDENT

Work and track earnings

Students see information tied to their account and assigned department.

  • Clock in/out and view time records
  • Review tuition balance and personal wallet
  • See shifts, earnings, and withdrawal history
  • Edit profile, upload photos, change password
SUPERVISOR

Manage a department

Supervisors operate within their assigned department.

  • Create and maintain department student accounts
  • Disable a student; edit ID, work assignment and rate
  • Set shifts and review department time logs
  • Manage tuition credit and record withdrawals
ADMINISTRATOR

Manage the whole system

Administrators have app-wide account and finance controls.

  • Create departments and all account roles
  • Assign users, set rates, change credentials
  • Correct time entries and manage schedules
  • Set balances, transfer credit, record payouts
  • Deactivate or permanently delete accounts
ⓘ
Department boundary: supervisor reads and financial actions are restricted to students in the supervisor’s department. Students should only access their own private records.
03 / DAILY USE

Core workflows

The main user journeys from entry to recorded work and the resulting financial balance.

◷

Time-in / time-out kiosk

The kiosk accepts a student number typed into the field or entered by a keyboard-emulating RFID reader. A successful scan looks up an active student and toggles their state: an open time record closes; otherwise a new record opens. A unique partial index prevents two open records for one student.

▣

Photo display & storage

Profile and cover images are processed to WebP and written to PROFILE_UPLOAD_DIR on the web server, not to the database. The kiosk gets a short-lived signed URL for the student’s avatar; without an upload, it displays the default avatar.

▤

Schedules and records

Administrators and supervisors maintain weekly student shifts. Students see their calendar and recent time entries; supervisors see department activity; administrators can add, edit, or remove time records with a reason attached to manual corrections.

✦

Feedback and profiles

App actions report success and errors using bottom-right toast notifications. Account profile details are editable; profile and cover pictures are server-side WebP files. Students and supervisors can change their password, while an administrator can override account credentials.

05 / MONEY FLOW

Financial rules

Work earnings first reduce the school tuition balance. Tuition credit can then be moved to a withdrawable wallet.

Tuition balance

set tuition balance − eligible earnings + credit already transferred. Eligible earnings come from completed time logs since financials_started_at. A negative result is credit owed by AUP to the student.

Personal wallet

opening wallet + all wallet transfers − all payouts. Allocation and withdrawal actions run in a PostgreSQL transaction and lock the student row before validating available funds.

!
Example: A student starts with ₱1,000 tuition owed and earns ₱1,250 after the balance is set. The tuition balance is −₱250, meaning ₱250 credit. A manager can allocate up to ₱250 to the personal wallet; any later withdrawal is recorded as a payout.
06 / PLATFORM CHANGE

Supabase → PostgreSQL

This is a full replacement of the database and authentication service—not just a change of connection string.

ConcernPrevious Supabase approachCurrent PostgreSQL approach
Database accessSupabase client API / PostgREST and Supabase RPC functions.Server-only pg connection pool in lib/db.ts; parameterized SQL from server code.
AuthenticationSupabase Auth users and access tokens.App-owned account password hashes using Node scrypt; sessions stored in the PostgreSQL sessions table.
AuthorizationSupabase Auth context and database RLS policies.Next.js server action/page role checks and department scoping in server queries. PostgreSQL is not exposed to browsers.
Database functionsRPC calls for functions such as kiosk toggling.Parameterized SQL and explicit transaction handling in application server actions.
Profile imagesPreviously relied on Supabase storage integration.WebP image files on the application server; PostgreSQL stores their file names.
Schema setupSupabase SQL files / dashboard migrations.database/schema.sql, applied with npm run db:migrate and tracked in schema_migrations.
!
Fresh start by design: existing Supabase users, passwords, records, and storage are not automatically copied. The new database starts empty; create the first administrator with npm run create-admin. Keep a separate backup of old data if it may be needed.
07 / FIRST-TIME DEPLOYMENT

Windows setup

PostgreSQL stays on the Windows host. The app connects over loopback; the tunnel points only to Next.js.

Install PostgreSQL

Install PostgreSQL for Windows. Use pgAdmin 4 or the bundled psql command line to create and inspect the database.

Create an app role and a fresh database

Connect as the PostgreSQL administrator. Pick a long password and use the same password in DATABASE_URL.

CREATE ROLE aupws_app LOGIN PASSWORD 'replace-with-a-strong-password';
CREATE DATABASE aup_work_scholars OWNER aupws_app;

Configure the app connection

Copy .env.example to .env.local, then set the database login and a random SESSION_SECRET (at least 32 bytes). Local connection format:

DATABASE_URL=postgresql://aupws_app:YOUR_PASSWORD@127.0.0.1:5432/aup_work_scholars
SESSION_SECRET=use-a-random-secret-of-at-least-32-bytes
DB_POOL_MAX=10
PROFILE_UPLOAD_DIR=./data/profile-uploads

If a database password includes URL-reserved characters, percent-encode it in the connection URL. Keep .env.local private and out of source control.

Install packages and apply the schema

Run from the project directory. The migration command is safe to repeat after the complete initial schema has been applied; it rejects partial schemas for inspection.

npm install
npm run db:migrate

Create the first administrator

This prompts for a name, email, and password (minimum 12 characters). Additional accounts are created in the admin or supervisor UI.

npm run create-admin

Run the web app

# Development
npm run dev

# Production
npm run build
npm start

For a Cloudflare Tunnel, route to the Next.js service (for example, localhost port 3000). Do not route the PostgreSQL port 5432 through the tunnel.

✓
Migration file: database/schema.sql. The runner is scripts/migrate.mjs; it applies the schema in a transaction and stores the initial version in schema_migrations.
08 / RUN IT SAFELY

Security & operations

With Supabase removed, the app server owns identity checks and the PostgreSQL connection. Protect both the app host and its secrets.

Authentication and sessions

  • Password hashes use salted scrypt; passwords are not stored in plaintext.
  • Browser cookie is HttpOnly, SameSite=Lax, and Secure in production.
  • The random cookie token is stored as a SHA-256 hash in PostgreSQL.
  • Sessions expire after seven days; sign out removes the current session.
  • Password changes revoke other sessions for that account.

Database boundary

  • Only server code imports the PostgreSQL pool.
  • Use parameterized SQL for values; never send DB credentials to the browser.
  • Keep PostgreSQL bound to localhost/private network.
  • Do not publish TCP 5432 in Cloudflare Tunnel or router firewall.
  • Supervisors’ department ownership is checked in server actions and scoped reads.

Backups and durability

  • Back up PostgreSQL regularly with pg_dump.
  • Back up PROFILE_UPLOAD_DIR separately; photos are files, not DB blobs.
  • Use persistent storage if the Next app runs as a service or in a container.
  • Practice restoring both a database dump and the photo directory.

Operational values

  • DATABASE_URL — server-side connection string.
  • SESSION_SECRET — signs short-lived kiosk image URLs.
  • DB_POOL_MAX — maximum pooled connections (default 10).
  • PROFILE_UPLOAD_DIR — image directory (default data/profile-uploads).
  • UI date formatting uses Asia/Manila; currency is PHP.
!
RLS changed: PostgreSQL is accessed by the app’s database role, not a browser Supabase client. Do not grant browser code database credentials. Maintain authorization checks on server actions and server reads whenever adding a new feature.

10 / QUICK REFERENCE

Glossary

Terms used throughout the application and this guide.

School tuition balanceAmount of tuition still owed. It may go below zero after earnings exceed tuition.
Tuition creditNegative tuition balance / amount earned beyond the configured tuition amount.
Personal walletWithdrawable amount: opening balance plus wallet allocations less payouts.
PayoutRecorded withdrawal from the personal wallet; not a time-earned payment calculation.
Wallet transferStaff action moving available tuition credit into the personal wallet.
Work assignmentStudent’s assigned job or duty description within the department.
RFID readerKeyboard-emulating card reader that submits a student identifier into the kiosk.
SessionServer-issued login state represented by a random cookie and stored token hash.
